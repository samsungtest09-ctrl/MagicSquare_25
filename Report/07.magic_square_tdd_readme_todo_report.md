## 4. 핵심 설계 결정

### 4.1 TDD 용어 고정

| 용어 | 정의 |
|---|---|
| **RED** | 테스트 실행 후 **의도한 이유로 실패하는지 확인**하는 단계 |
| **GREEN Task** | RED 실패를 통과시키기 위한 **최소 구현 작업 후보** (실제 구현 아님) |
| **REFACTOR Candidate** | GREEN 이후 **동작 불변** 구조 개선 **후보만** 기록 |

### 4.2 Track 분리

- **Boundary RED:** `ERR-BND-001`~`005`, 출력 길이·1-index
- **Logic RED:** BlankFinder, MissingNumberFinder, Validator, Solver
- **Integration RED:** TD-001/002 E2E, Boundary 오류 전파

### 4.3 오류 코드 가정 (PRD 검토 연동)

| 코드 | 조건 |
|---|---|
| ERR-BND-001 | None 입력 |
| ERR-BND-002 | 4×4 형상 위반 |
| ERR-BND-003 | 빈칸 개수 ≠ 2 |
| ERR-BND-004 | 값 범위 위반 |
| ERR-BND-005 | 0 제외 중복 |
| ERR-DOM-001 | small-first·reverse 모두 실패 |

## 9. 결론

- PRD 기반 **TDD 시작 준비**에 필요한 추적 보드(To-Do)와 **프로젝트 시작 README 초안**이 대화 산출로 완료되었다.
- 15개 필수 Scenario, RED Test ID, Test Skeleton 후보, GREEN/REFACTOR 후보, ECB Layer, Code Target이 1:1 연결되었다.
- 구현·테스트 코드는 의도적으로 미작성하였으며, 다음 실무 단계는 **Test Skeleton + RED 실패 확인**이다.
- PRD 원본·일부 Report 파일명은 워크스페이스와 README 참조 경로 간 차이가 있으므로, 문서 동기화를 권장한다.
