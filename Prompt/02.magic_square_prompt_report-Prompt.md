## [T1] 어시스턴트 산출 프롬프트
```text
당신은 시니어 소프트웨어 아키텍트이자 TDD 코치다.
목표는 **Magic Square 4x4 구현을 위한 TDD 설계 문서**를 작성하는 것이다.

중요:
- 지금은 구현 코드 작성 금지
- 테스트 코드의 전체 구현도 금지 (필요 시 테스트 스켈레톤/의사코드만 제시)
- 결과물은 “설계 문서”여야 하며, 실행 가능한 개발 계획이어야 한다
- 문서는 한국어로 작성한다
- Markdown 형식으로 작성한다
- 모호한 부분은 합리적 가정을 세우고, 문서 상단에 “가정(Assumptions)”으로 명시한다

다음 구조를 정확히 따라 문서를 작성하라:

# Magic Square 4x4 TDD 설계 문서

## 1. 문제 정의
- Magic Square의 수학적 정의
- 4x4 범위에서의 입력/출력 기대
- 성공 조건과 실패 조건

## 2. 요구사항 명세
### 2.1 기능 요구사항 (FR)
- FR-01, FR-02 형식으로 번호화
- 각 요구사항은 검증 가능한 문장으로 작성

### 2.2 비기능 요구사항 (NFR)
- 성능, 확장성, 테스트 용이성, 가독성, 유지보수성
- 정량/정성 기준 포함

## 3. 도메인 모델 및 데이터 설계
- 핵심 엔티티/값 객체 정의 (예: Board, Cell, Constraint 등)
- 데이터 구조 후보 비교 (2개 이상)
- 최종 선택과 이유

## 4. 알고리즘 설계
- 가능한 접근법 최소 2가지 제시 (예: 백트래킹, 패턴 기반 생성)
- 시간/공간 복잡도 비교
- 4x4에 최적화된 최종 알고리즘 선택 근거
- 의사코드(pseudocode) 포함

## 5. TDD 전략 (Red-Green-Refactor)
- 개발 단계를 작은 사이클로 분해
- 각 사이클마다:
  - 실패 테스트(RED)
  - 최소 구현(GREEN)
  - 리팩터링(REFACTOR)
- 우선순위와 의존관계 명확화

## 6. 테스트 설계
### 6.1 단위 테스트 케이스 목록
- 테스트 ID, 목적, 입력, 기대 결과, 실패 시 의미
- 정상/경계/예외/오류 입력 포함

### 6.2 속성 기반 검증 규칙
- 모든 행/열/대각선 합 동일성
- 숫자 중복 금지/범위 검증
- 불변 조건(invariants)

### 6.3 통합/회귀 테스트 전략
- 리팩터링 후 안정성 보장 방법
- 회귀 테스트 묶음 구성 기준

## 7. 구현 로드맵
- 마일스톤 단위(작은 PR/커밋 기준)로 제시
- 각 마일스톤의 완료 조건(DoD) 포함
- 예상 리스크와 대응 전략

## 8. 품질 게이트(Definition of Done)
- 문서/테스트/코드 품질 기준 체크리스트
- “완료” 판정 기준을 Yes/No로 점검 가능하게 작성

## 9. 부록
- 샘플 입출력 시나리오
- 실패 사례 예시
- 향후 일반화(예: NxN 확장) 고려사항

출력 규칙:
- 표가 필요한 경우 Markdown 표 사용
- 각 섹션은 누락 없이 작성
- 너무 추상적으로 쓰지 말고, 실제 구현자가 바로 착수 가능한 수준으로 구체화
- 마지막에 “즉시 실행 가능한 첫 번째 TDD 사이클 3개”를 체크리스트로 요약
```

## [T2] 사용자 요청
Dual-Track UI + Logic TDD 및 Clean Architecture 설계 전문가 조건으로, 고정 입력/출력 계약과 지정된 출력 구조를 따르는 프롬프트를 작성하라.

## [T2] 어시스턴트 산출 프롬프트
```text
역할:
당신은 Dual-Track UI + Logic TDD 및 Clean Architecture 설계 전문가입니다.

프로젝트:
Magic Square (4x4) — TDD 연습용

핵심 목적:
알고리즘 난이도 자체보다, 아래 훈련 목표를 우선합니다.
1) 레이어 분리
2) 계약(Contract) 기반 테스트
3) Red-Green-Refactor 중심 리팩토링

절대 제약:
- 구현 코드 작성 금지
- 테스트 “구현 코드” 작성 금지 (테스트 설계/케이스 명세만 허용)
- UI는 실제 화면이 아니라 입력/출력 Boundary로만 정의
- Data Layer는 DB가 아니라 저장/로드 인터페이스 수준(메모리/파일 교체 가능)
- 입력/출력 계약은 아래 정의를 고정 사용
- 모호한 표현 금지 (“적절히”, “충분히”, “가능하면” 등 금지)
- 모든 규칙은 테스트로 검증 가능해야 함

입력 계약 (고정):
- 타입: 4x4 int[][]
- 0은 빈칸
- 빈칸 개수: 정확히 2개
- 값 범위: 0 또는 1~16
- 0 제외 중복 금지

출력 계약 (고정):
- 타입: int[6]
- 좌표는 1-index
- 반환 형식: [r1,c1,n1,r2,c2,n2]
- n1,n2는 두 누락 숫자
- (작은수→첫빈칸, 큰수→둘째빈칸) 조합이 마방진이면 그 순서 반환
- 아니면 반대로 반환

작성 지침:
- 한국어로 작성
- Markdown으로 작성
- 표/체크리스트 적극 사용
- 각 규칙에 대해 “검증 방법(어떤 테스트로 확인하는지)”을 반드시 연결
- 섹션 누락 금지
- 각 섹션은 실행 가능한 수준으로 구체화

출력 형식 (반드시 아래 구조와 제목을 그대로 사용):

# 1) Logic Layer (Domain Layer) 설계
## 1.1 도메인 개념
- Entities / Value Objects / Domain Services 목록과 책임(SRP)

## 1.2 도메인 불변조건(Invariants)
- 행/열/대각선 합 일치, Magic Constant 등
- 각 invariant별 “검증 테스트 항목” 명시

## 1.3 핵심 유스케이스(도메인 관점)
- 빈칸 찾기, 누락 숫자 찾기, 마방진 판정, 두 조합 시도
- 유스케이스별 입력/출력/실패조건

## 1.4 Domain API(내부 계약)
- 메서드 시그니처 수준(코드 X)
- 입력/출력/실패조건
- 사전조건(Precondition)/사후조건(Postcondition)

## 1.5 Domain 단위 테스트 설계(RED 우선)
- 테스트 케이스 목록(정상/비정상/엣지)
- 각 테스트가 보호하는 invariant 명시
- Red → Green → Refactor 순서의 최소 사이클 제시

# 2) Screen Layer (UI Layer) 설계 (Boundary Layer)
## 2.1 사용자/호출자 관점 시나리오
- “행렬 입력 → 검증 → 결과 출력” 흐름

## 2.2 UI 계약(외부 계약)
- Input schema / Output schema / Error schema
- 스키마 필드 타입/제약/예시

## 2.3 UI 레벨 테스트(Contract-first, RED 우선)
- 잘못된 크기
- 빈칸 개수 오류
- 값 범위 오류
- 중복 오류
- 반환 포맷 검증
- Domain은 Mock으로 가정

## 2.4 UX/출력 규칙
- 에러 메시지 표준
- 정확한 문구 규칙(템플릿/코드/필드 포함)

# 3) Data Layer 설계 (Data Layer)
## 3.1 목적 정의
- 저장/로드 필요성과 범위(학습용)

## 3.2 인터페이스 계약
- 예: MatrixRepository.save/load (메서드 수준, 코드 X)
- 저장 대상: 입력 행렬, 실행 결과(선택), 에러 로그(선택 여부 명시)

## 3.3 구현 옵션 비교(메모리/파일)
- 옵션 A: InMemory
- 옵션 B: File(JSON/CSV)
- 비교표 작성 후 추천안 1개 선택 + 이유

## 3.4 Data 레이어 테스트
- 저장/로드 정합성
- 예외(파일 없음/형식 오류)
- 불변조건(4x4 유지)

# 4) Integration & Verification (통합 및 검증)
## 4.1 통합 경로 정의
- UI → Application(선택) → Domain → Data
- 의존성 방향과 경계 규칙 명시

## 4.2 통합 테스트 시나리오
- 정상 시나리오 2개 이상
- 실패 시나리오 3개 이상 (입력 오류, 도메인 실패, 데이터 실패)

## 4.3 회귀 보호 규칙
- 기존 테스트 유지 정책
- 변경 금지 규칙(계약/출력 포맷)

## 4.4 커버리지 목표
- Domain Logic 95%+
- UI Boundary 85%+
- Data 80%+

## 4.5 Traceability Matrix (필수)
- 열(컬럼) 고정:
  Concept(Invariant) | Rule | Use Case | Contract | Test | Component
- 최소 10행 이상 작성

추가 산출물(필수):
1) “테스트 우선순위 체크리스트” (P0/P1/P2)
2) “리팩토링 트리거 조건” 체크리스트
3) “계약 위반 시 실패 응답 표준” 표

최종 자기검증(문서 마지막에 YES/NO로 출력):
- 구현 코드가 포함되지 않았는가?
- 테스트 구현 코드가 포함되지 않았는가?
- 입력/출력 계약을 고정 준수했는가?
- 모든 규칙이 테스트 가능하게 작성되었는가?
- 4개 대섹션과 모든 하위섹션을 빠짐없이 작성했는가?
- Traceability Matrix를 포함했는가?
```
